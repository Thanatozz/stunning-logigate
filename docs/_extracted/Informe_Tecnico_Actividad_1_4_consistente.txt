1. Introducción
El presente informe documenta el proceso de implementación del prototipo simulado correspondiente al Avance #3 de la asignatura Integración de Competencias III. Este avance constituye la validación de la factibilidad técnica del diseño conceptual presentado en el Avance #2, utilizando el simulador en línea Wokwi para recrear el circuito IoT en un entorno virtual controlado.
El prototipo simula un sistema IoT de monitoreo de acceso vehicular compuesto por un módulo ESP32 con dos sensores infrarrojos para detección bidireccional, un servo motor SG90 como barrera vehicular simulada, un botón pulsador para apertura manual de emergencia, y LEDs indicadores de estado. La simulación valida la lógica de detección, el control de la barrera en sus tres modos de operación (automático, manual remoto y manual físico), y el flujo general del sistema.
Dado que Wokwi no soporta el módulo ESP32-CAM con cámara OV2640 ni la conexión a APIs externas como Plate Recognizer, la funcionalidad de reconocimiento de patentes y la integración con Firebase se documentan mediante capturas y descripciones de cómo operarían los datos en el prototipo real. El informe incluye la estructura de datos esperada, el flujo de información entre componentes, y el diseño del dashboard que visualizaría los datos en un entorno productivo.
2. Herramientas Utilizadas
Nota: Wokwi no dispone del módulo ESP32-CAM con cámara OV2640. Para la simulación, se utilizó una placa ESP32 genérica y la funcionalidad de captura de imagen + reconocimiento de patentes se simuló mediante datos hardcodeados en el firmware (patentes predefinidas que se “leen” al activarse el sensor). La integración real con Plate Recognizer API y Firebase se implementará en la etapa de prototipo físico.

4. Firmware — Lógica Implementada
El firmware se desarrolló en C/C++ compatible con Arduino IDE y se ejecutó en el simulador Wokwi. Aunque la simulación no incluye cámara ni conexión real a APIs, la lógica completa del sistema está implementada y validada mediante el monitor serial.
4.1 Flujo de Operación Simulado
El firmware implementa el siguiente flujo, visible en el monitor serial de Wokwi:
1. El ESP32 monitorea GPIO 13 (sensor exterior) y GPIO 14 (sensor interior) esperando detección.
2. Al detectar presencia en cualquiera de los dos sensores, se imprime en serial: “[DETECCIÓN] Sensor S1/S2 activado”.
3. Se simula la captura de imagen y lectura OCR: el firmware selecciona una patente de un array predefinido (ej: “AB-1234”, “CD-5678”, “XX-9999”) y asigna un score de confianza aleatorio entre 70% y 99%.
4. Se aplica el filtro de confianza: si el score < 80%, se imprime “[DESCARTADO] Confianza 74% < umbral 80%” y el evento se ignora.
5. Se verifica si la patente está en el array de vehículos autorizados (simula la consulta a Firebase /vehiculos/). Si no está, se imprime “[ALERTA] Vehículo no autorizado: XX-9999”, el LED rojo se enciende, y la barrera NO se abre.
6. Si la patente está autorizada, se consulta el array local de vehículos presentes (simula /estadoPlanta/vehiculosPresentes/): si no está presente → INGRESO; si ya está presente → SALIDA.
7. Se imprime el resultado: “[INGRESO] AB-1234 registrado. Camiones en planta: 3” o “[SALIDA] AB-1234 registrado. Permanencia: 45 min. Camiones en planta: 2”.
8. El LED verde se enciende y el servo gira a 90° (barrera abre). Después de 5 segundos, el servo vuelve a 0° (barrera cierra) y el LED se apaga.
9. En cualquier momento, si se presiona el botón (GPIO 15), la barrera abre inmediatamente y se imprime “[MANUAL] Apertura de emergencia física”.

4.3 Control de Barrera — Tres Modos
La simulación valida los tres modos de operación de la barrera:
Modo automático: Al detectar un vehículo autorizado, el servo gira automáticamente a 90° (abierto) y regresa a 0° (cerrado) tras 5 segundos. El LED verde se enciende durante la apertura. Si el vehículo no está autorizado, el servo no se mueve y el LED rojo se enciende.
Modo manual físico (botón GPIO 15): Al presionar el botón en Wokwi, la barrera abre inmediatamente sin importar el estado del sistema. Se imprime en serial “[MANUAL] Apertura de emergencia física”. Este modo siempre funciona, incluso si el sistema principal está en error.
Modo manual remoto (simulado en serial): En el prototipo real, el supervisor abriría la barrera desde el dashboard Vue.js enviando un comando a Firebase. En la simulación, este modo se activa enviando el carácter “A” por el monitor serial de Wokwi, lo que simula la recepción de un comando remoto.

8. Problemas Detectados y Soluciones Aplicadas
Nota: Los problemas comunes en simulaciones Wokwi incluyen: conflictos de GPIO (pines reservados del ESP32), servo motor no responde (pin incorrecto o librería no compatible), sensor PIR con tiempos de activación largos, botón con rebote (bouncing), y lógica de cooldown interfiriendo con detecciones consecutivas.
9. Limitaciones de la Simulación y Próxima Etapa
9.1 Limitaciones de la Simulación en Wokwi
La simulación en Wokwi valida la lógica del sistema pero presenta las siguientes limitaciones respecto al prototipo real:
•  No se puede simular la cámara OV2640 ni la captura de imágenes JPEG. El reconocimiento de patentes se simuló con datos hardcodeados.
•  No se puede conectar a APIs externas reales (Plate Recognizer) desde Wokwi.
•  No se puede conectar a Firebase Realtime Database. La lógica de estado se implementó con variables locales en el ESP32.
•  No se puede implementar el dashboard Vue.js conectado en tiempo real. Se presentaron mockups con datos esperados.
•  Los sensores PIR de Wokwi tienen comportamiento ligeramente diferente a los sensores ultrasónicos HC-SR04 de obstáculo físicos.
•  La alimentación eléctrica no es un factor en simulación (en el prototipo real, el ESP32-CAM requiere 5V 2A).
9.2 Próximos Pasos para el Prototipo Físico
Para evolucionar de la simulación al prototipo físico funcional, se deben completar las siguientes tareas:
1. Adquirir el hardware real (ESP32-CAM + sensores ultrasónicos HC-SR04 + servo + protoboard).
2. Migrar el firmware de Wokwi a Arduino IDE, reemplazando los datos hardcodeados por la integración real con Plate Recognizer API.
3. Configurar Firebase (Realtime Database, Authentication, Hosting) e integrar con el firmware.
4. Desarrollar el dashboard Vue.js con los composables de Firebase para actualización en tiempo real.
5. Conectar el control de barrera remoto (dashboard → Firebase → ESP32-CAM → servo).
6. Realizar pruebas de integración end-to-end con patentes impresas en papel.
7. Desplegar el dashboard en Firebase Hosting para acceso remoto.
10. Conclusiones
La simulación del prototipo en Wokwi valida la factibilidad técnica de la lógica central del sistema de monitoreo de acceso vehicular. A pesar de las limitaciones inherentes del simulador (ausencia de cámara, APIs y conectividad cloud), se logró demostrar el correcto funcionamiento de los siguientes aspectos críticos:
•  La detección bidireccional con dos sensores ultrasónicos HC-SR04 funciona correctamente, activando la secuencia de procesamiento sin importar la dirección de aproximación del vehículo.
•  La lógica de stateful event detection (ingreso/salida por estado) opera según lo diseñado, determinando correctamente el tipo de evento y calculando tiempos de permanencia.
•  El filtrado de falsos positivos en dos capas (confianza OCR + patente registrada) descarta efectivamente los eventos inválidos.
•  El control de barrera funciona en sus tres modos: automático (vehículo autorizado), manual físico (botón de emergencia) y manual remoto (comando serial simulando dashboard).
•  Los indicadores LED reflejan correctamente el estado del sistema (verde = autorizado, rojo = no autorizado/alerta).
La simulación sirve como base sólida para la implementación del prototipo físico, ya que la lógica del firmware está validada y solo requiere reemplazar los datos simulados por las integraciones reales (cámara, Plate Recognizer, Firebase). La arquitectura modular del código facilita esta transición sin necesidad de reescribir la lógica de negocio.
Criterio de consistencia aplicado: prototipo de 1 carril con dos sensores ultrasónicos HC-SR04 instalados en el mismo lado físico del portón, cámara fija y lógica de dirección (ingreso/salida) resuelta por software mediante estado del vehículo.
